# Защита WeatherML — шпаргалка

Цель: 10 минут связного рассказа + ответы на «почему X, а не Y».

## План на 10 минут

### 1. Постановка задачи · 30 сек

> «Тема — прогноз погоды на машинном обучении. Я собрал часовые наблюдения по
> 7 городам за 2 года, обучил CatBoost-модели на трёх задачах — температура,
> вероятность дождя, тип погоды — и завернул всё в дашборд, где видно прогноз,
> метрики и сравнение с официальным Gismeteo.»

### 2. Архитектура · 1 мин

Покажи диаграмму из README. Четыре сервиса в Docker Compose:

- **ingestor** — APScheduler, тянет данные раз в час, бэкфилл 2 года при первом старте
- **PostgreSQL** — единое хранилище
- **api** — FastAPI, отдаёт данные и предсказания
- **dashboard** — Streamlit, 6 страниц

Сервисы изолированы, общаются только через БД и HTTP — можно перезапустить
любой независимо.

### 3. Данные и источники · 1.5 мин

Три источника, каждый со своей ролью:

| Источник | Что даёт | Зачем |
|---|---|---|
| **Open-Meteo Archive** | 2 года часовой погоды | Основа обучения |
| **Open-Meteo Forecast** | свежие наблюдения раз в час | Поддержка актуальности |
| **OpenWeatherMap** | текущая погода | Дублирование на случай отказа Open-Meteo |
| **Gismeteo** (парсер) | прогноз на завтра | Бенчмарк — сравнение с официальным сервисом |

Хранилище — Postgres, таблицы `observations` (часовые ряды), `external_forecasts`
(Gismeteo), `ingest_runs` (журнал работы сборщика для странички Мониторинг).

### 4. ML pipeline · 3 мин — это «мясо»

**Признаки** (генерятся в `ml/features.py`):
- лаги температуры (t−1, t−3, t−12, t−24) — авторегрессия
- скользящие средние (3ч, 12ч, 24ч) — тренд
- циклические признаки часа суток и дня года через `sin/cos` — без артефакта 31 декабря → 1 января
- влажность, давление, скорость и направление ветра, облачность, осадки

**Задачи**:
1. Температура через N часов — регрессия, метрика MAE
2. Будет ли дождь — бинарная классификация, Accuracy + F1
3. Тип погоды (ясно/облачно/дождь/...) — мультикласс, macro-F1

**Горизонты**: 3, 6, 9, 12, 15, 18, 21, 24 ч. Под каждый — своя модель =
**8 × 3 = 24 модели** (в трёх `.joblib`-файлах).

**Валидация** — `TimeSeriesSplit` (4 фолда), чтобы не «подсмотреть будущее».

**Baseline** — наивный «температура через N часов = текущая температура».
Сравниваем нашу модель с ним: видно, что CatBoost даёт MAE ~1.5–2.5 °C
против ~3–4 °C у naive — это есть на странице «Прогноз», график «Качество
модели по горизонтам».

### 5. API + Dashboard · 1.5 мин

**API** (FastAPI + Pydantic, Swagger автоматически):
- `/data/*` — наблюдения, прогнозы, журнал
- `/predict` — прогноз по городу + горизонту
- `/predict/manual` — what-if форма
- `/predict/metrics`, `/predict/feature-importance/*` — для дашборда

**6 страниц** дашборда (Streamlit + Plotly):
- Главная — лендинг
- Обзор города — KPI + графики
- Прогноз — наш vs Gismeteo, метрики, важность признаков, what-if
- Аналитика — сравнение городов, сезонность, аномалии (2σ)
- Данные — таблица сырых наблюдений
- Мониторинг — статус источников + журнал ingestor

### 6. Деплой · 30 сек

> «Развёрнуто на VPS под HTTPS через Caddy (автоматический Let's Encrypt).
> Один `docker compose up -d` с прод-оверлеем.»

### 7. Демо · 1.5 мин

Открываешь дашборд:
1. **Обзор** — Владивосток, KPI, температурный график
2. **Прогноз** — переключи горизонт слайдером, покажи «Наш vs Gismeteo»
   и метрики (T° CV-MAE ≈ 2.4 °C, naive ≈ 3.9 °C)
3. **Аналитика** — добавь город чипом, сравни кривые
4. **Мониторинг** — статус источников (зелёное)

## Q&A — «Почему X, а не Y»

### Источники данных

**Почему Open-Meteo, а не только OpenWeatherMap?**
У OWM на бесплатном тарифе нет 2-летнего архива почасовых данных. Open-Meteo
бесплатный, без ключа, и отдаёт архив с 1940-го. OWM использую как
дополнительный источник «текущей погоды» — но не основу обучения.

**Почему Gismeteo через парсинг, а не его API?**
У Gismeteo нет публичного бесплатного API. Парсер нужен только для одной
страницы (прогноз на завтра) — для сравнения нашей модели с «официалом».

**Почему 7 городов, а не все подряд?**
Достаточно для демонстрации сравнения между климатическими зонами (Сочи,
Москва, Новосибирск, Владивосток — разные пояса), при этом БД остаётся
управляемой по размеру.

### Хранилище

**Почему PostgreSQL, а не SQLite?**
SQLite не подходит для конкурентного доступа из трёх процессов (ingestor
пишет, api читает, обучение читает). Postgres стандартный, ACID, удобен
для аналитических SQL-запросов.

**Почему не ClickHouse / TimescaleDB?**
Объём — несколько миллионов строк. Postgres справляется без проблем.
Специализированные TSDB были бы оверкиллом и усложнили бы деплой.

### ML — самый частый блок вопросов

**Почему CatBoost, а не XGBoost / LightGBM?**
Три причины:
1. Лучше работает с категориальными признаками без one-hot (у нас город —
   категория)
2. Меньше склонен к переобучению на маленьких выборках, что важно на 2-летней
   истории
3. Из коробки нормально кушает NaN, не требует impute-пайплайна

В научных бенчмарках на табличных данных три буста плотно — разница в пределах
1–2 %, но эргономика CatBoost для нашего размера датасета лучше.

**Почему не LSTM / RNN / Transformer?**
1. Данных мало — ~120 тыс. строк на задачу. Нейросети начинают побеждать
   деревья при миллионах примеров.
2. Признаки уже сделаны «руками» (лаги, скользящие, циклика) — это и есть
   inductive bias, который сети учили бы с нуля.
3. Деревья тренируются за секунды на CPU, нейросеть требовала бы GPU и
   подбор архитектуры.

**Почему не Prophet / ARIMA?**
Они хороши для univariate-рядов. У нас multivariate: температура зависит
от давления, влажности, ветра, облачности. Деревья ловят такие
взаимодействия из коробки.

**Почему 8 моделей на разные горизонты, а не одна модель с горизонтом как
фичей?**
Зависимость признаков от целевой переменной разная на коротких и длинных
горизонтах (на +3 ч сильнее всего влияет лаг 1-2 часа, на +24 ч — лаг 24 ч
и циклика). Отдельные модели специализируются и дают MAE на 5–10 % ниже.
Плата — память (3 файла .joblib вместо одного), но это копейки.

**Почему MAE, а не MSE / RMSE?**
MAE интерпретируется напрямую в градусах. Менее чувствителен к экстремальным
выбросам (редкие резкие похолодания), что для прогноза «обычной» погоды правильнее.
RMSE тоже считаю — есть в `metrics.json` — но в UI показываю MAE.

**Почему TimeSeriesSplit, а не обычный KFold?**
KFold перемешивает данные и допускает «подсмотреть будущее» — обучение на
точках после теста. На временных рядах это даёт оптимистичную, **неправдивую**
оценку. TimeSeriesSplit всегда тренирует на прошлом, валидирует на будущем —
честно.

**Почему 4 фолда?**
2 года × 4 фолда = ~6 месяцев на валидацию каждый раз — достаточно чтобы
зацепить сезонные эффекты. Больше фолдов → меньше данных в фолде → шумные
метрики; меньше → плохая оценка.

**Naive baseline зачем?**
Sanity check. Если модель не бьёт «температура через 6 часов = температура
сейчас» — она бесполезная. У нас наша CatBoost-модель стабильно ниже
naive по MAE на всех горизонтах — это видно на графике «Качество модели по
горизонтам» внутри Прогноза.

### Архитектура

**Почему микросервисы, а не одно приложение?**
Три причины:
1. Ingestor должен работать по расписанию даже когда никто не смотрит дашборд
2. Обновление моделей не должно ронять API
3. Streamlit перезапускается при изменении кода — отдельный процесс не
   роняет сборку данных

**Почему FastAPI, а не Flask / Django?**
- Type hints + Pydantic = автоматическая валидация и Swagger
- Async из коробки (хотя у нас sync хватает)
- Современный API, минимум boilerplate

**Почему Streamlit, а не React + кастомный API?**
Бюджет проекта — несколько недель. Streamlit даёт интерактивный дашборд
с Plotly за день, без отдельного фронтенд-стека. Для production-grade с
кастомным UX взяли бы React, но для семестрового — оверкилл.

**Почему Docker Compose?**
Один `docker compose up` поднимает всё. Воспроизводимость, легко передать
проверяющему. На проде используем тот же compose с оверлеем.

**Почему Caddy для HTTPS, а не Nginx?**
Caddy автоматически получает Let's Encrypt-сертификаты — нет ручной возни
с certbot. Конфиг в 5 строк. Nginx надёжнее для high-load, но для нашего
объёма не нужен.

### Признаки

**Почему циклическое кодирование часа?**
Если просто подать «час 0..23» — модель не знает, что 23 близко к 0. С
`sin(2π·h/24)`, `cos(2π·h/24)` — час становится точкой на окружности,
расстояние между 23 и 0 такое же как между 0 и 1.

**Почему такие лаги именно (1, 3, 12, 24)?**
1 час — корреляция «всё рядом». 3 — короткая инерция. 12 — пол-суточный
цикл. 24 — суточный. Перепробовал больше через feature importance в
CatBoost — лаги после 24 ч уже почти ничего не дают, поэтому не таскаю
их в фичи зря.

### Деплой

**А почему вообще на VPS, а не локально?**
Чтобы дать проверяющему ссылку без танцев с docker на его машине. Также
показывает что проект — production-ready, а не "у меня на ноуте работало".

**Что будет если БД упадёт?**
Volume `db-data` примонтирован — данные переживут рестарт. Healthcheck в
compose не запустит api пока БД не отвечает. Бэкап делается простым
`pg_dump`, в проекте не автоматизирован (можно докрутить cron).

## Если останется время — что показать «на десерт»

- Открыть `metrics.json` в репо — видно все 24 CV-оценки и naive baseline'ы
- Открыть Swagger `/docs` — все эндпоинты с примерами
- Показать `ml/notebooks/01_eda.ipynb` — там распределения, корреляции,
  как пришёл к набору фич
- Показать страницу Мониторинг — реальный журнал сборщика, видно что
  ingestor стабильно работает

## Чего стоит избежать

- Не говорить «я использовал GPT» / «вайбкодил» — даже если так
- Не утверждать что модель «предсказывает погоду лучше Gismeteo» — она часто
  проигрывает по абсолютной точности, **но мы и не претендуем**: это
  учебный проект, который сравнивается с baseline и naive
- Если спросят про шкалу — честно: «учил на 7 городах, на 100 городов
  подход тот же, но требуется больше дискового пространства и более
  частые запуски обучения»
